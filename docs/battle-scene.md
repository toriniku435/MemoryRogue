# BattleScene

Detail doc for `Live2DCardRogue.BattleScene.*` (`Assets/Scripts/Scenes/BattleScene/`), imported from the root `CLAUDE.md`. Read that file first for the general layering/wiring conventions this scene follows — this file only covers what's specific to BattleScene.

## Composition root

`BattleSceneInitializer.Initialize(data)` (called by `SceneInitializerBase`; a null `data` falls back to the Inspector mock) builds, in order: the models (`CreateModels`, gathered in a private `BattleModels` holder: `BattleCardPilesModel` (deck/hand/discard/purge and the returning pile), `BattleTokenModel`, `CommandHistoryModel`, `BattlePhaseModel`, `CardCommandModel` (the execution list), `CardSelectionModel` (the card waiting for a target), the focus, preview, current-action and priority-target models and the `EnemyPartyModel`), the command use cases (`BattleDrawUseCase`, `BattleCommandQueueUseCase`, `BattleCommandExecuteUseCase`, `BattleTurnEndUseCase`, sharing one `BattleTargetResolver`; see "Command use cases" below), `BattlePhaseDirector`, the pile, unit and target presenters, the battle log (`BattleLogWiring`, which connects `BattleLogRecorder` to the director and the use case), the windows, then starts the battle loop. Every presenter goes through `Add`, and `OnDestroy()` disposes them in reverse. The enemies come from `CreateEnemies()`, which matches the enemy data against `BattleSceneViewContainer.EnemyStatusViews` **in step, front to back** (hiding the views left over) and has `UseCase/BattleEnemyFactory` build one `UnitStatusModel` per entry (with the `EnemyStrength` and the initial status effects) as a `BattleEnemy` (`Data/BattleEnemy.cs`), which all go into an `EnemyPartyModel` (`Models/EnemyPartyModel.cs`) — the one place that knows the order, and therefore both who acts next and who a dead target's card is re-aimed at. The same `EnemyData` asset can appear more than once — only the `UnitStatusModel` is per-body — which is how the scene currently fields two Trojans. The deck handed over is **shuffled** here once (`deck.Shuffle()`), so the first hand is not simply the order the deck was listed in. Views left over are hidden (a stage may field fewer enemies); if there are more enemies than views, the extra enemies are dropped and an error is logged, because a silently missing enemy is much harder to notice than a red line. Every `UnitPresenter`, player's and enemies', is wired identically (`canBeTargeted` / `onTargetClicked` both point at `BattleCommandQueueUseCase`), because any of them can be the one the player picks — which side a given card allows is the use case's call, not the wiring's. See the file itself for the exact wiring order — it's short and is the authoritative source for "what depends on what."

## Turn/phase loop

`BattlePhaseDirector.StartBattleLoop` runs an async loop (UniTask) while both units have HP: `ExecutePlayerTurnAsync` → `ExecuteEnemyTurnAsync` → repeat. `BattlePhaseModel.CurrentPhase` (`BattlePhase.Draw` / `Player` / `PlayerExecution` / `Enemy`) updates as the loop progresses and is the single source of truth other code reads to gate behavior — e.g. `BattleCardHandPilePresenter` ignores a card click unless `CurrentPhase == BattlePhase.Player`, and `BattleCommandListPresenter` leaves the Execute button `interactable` only in that phase. `Draw` is only ever active synchronously for the duration of `BattleDrawUseCase.Draw()` inside `ExecutePlayerTurnAsync` — nothing can observe it mid-frame, it exists so `BattlePhaseModel.OnPhaseChanged` subscribers get a distinct notification for the draw step if one is ever needed.

`PlayerExecution` covers the stretch after the Execute button is pressed, while the queued cards are being played one at a time. It exists so that "it is the player's turn" and "the player may act" stop being the same fact: without it, `Player` would still be the current phase while the list resolves, and a click could queue a card into a list that is already being consumed.

Each unit's `UnitStatusModel.StartTurn()` / `EndTurn()` bracket **its own** turn inside the matching `Execute*TurnAsync` — so a unit's status-effect turn hooks fire on its own turn only. Note that `BattleTurnEndUseCase.EndPlayerTurn()` is a different thing: it discards the hand, restores stamina and clears anything left in the execution list, while `UnitStatusModel.EndTurn()` runs the status-effect hooks and purges expired effects. Both happen, in that order, and both are called by the director — no button calls either one.

The player phase blocks on a `UniTaskCompletionSource` that only completes when `CardCommandModel.OnExecuteRequested` fires, raised by `BattleCommandQueueUseCase.RequestExecuteCommands()` (the Execute button, wired by `BattleCommandListPresenter`). The event sits on the model both sides already hold, so the director subscribes to it in its own constructor and unsubscribes in `Dispose()`, and no use case references `BattlePhaseDirector`.

`ExecutePlayerCommandsAsync` then sets the phase to `PlayerExecution` and calls `BattleCommandExecuteUseCase.ExecuteNext()` once per `PlayerCommandDelayMs` until the list is empty, breaking early when the enemy's HP reaches 0 so the rest of the list isn't spent on a corpse. It then holds for `PlayerTurnEndDelayMs` before returning, so the last card's result is still on screen when the caller sweeps the hand into the discard — but only if something was actually played, so ending a turn with an empty list costs no wait. It deliberately mirrors `ExecuteEnemyTurnAsync`: the director owns the pacing, the model owns how much can happen. The list length is already bounded by `CardCommandModel`'s own max count, so the loop needs no counter of its own — "until the list is empty" is safe.

`ExecuteEnemyTurnAsync` walks `EnemyPartyModel.Enemies` **in order, front to back**, and each enemy finishes its whole turn before the next one starts. The planned cards are cut to `enemy.Status.CalculateLimit(StatLimitType.ActionCount, planned)` first, which is how a stunned enemy skips its turn: `StartTurn()`, then a `foreach` over `BattleEnemy.PlannedCards` (planned by `EnemyData.PickCards()` **once**, at the start of the player's turn — see "Enemy intent and glitch" below) waiting `EnemyActionDelayMs` before each action and calling `BattleCommandExecuteUseCase.ExecuteEnemyCard(card, enemy.Status, playerModel)`, then `EndTurn()`. A defeated enemy is skipped outright, so it neither acts nor runs its status-effect turn hooks. The whole turn — how many actions, which cards, in what order — is planned by the `[SerializeReference] IEnemyCardPicker` on the enemy's `EnemyData` asset (see "Enemy data" in the root doc), so `BattlePhaseDirector` holds the `EnemyData` but knows nothing about the selection logic. That is the whole enemy "AI" so far.

That loop needs no guards of its own either: `PickCards()` always returns a non-null list whose length is already bounded by the asset's action counts. The only early exit is `_playerModel.CurrentHp == 0`, checked both inside one enemy's actions and between enemies, so a dead player doesn't keep getting hit for the rest of the planned actions.

The battle ends when the player dies or when **every** enemy is defeated (`EnemyPartyModel.AreAllDefeated`), which is also what stops the player's execution list early. A single enemy dying part-way through the list does not stop it: `BattleCommandExecuteUseCase.ExecuteNext` re-aims each card at execution time if its target is already down (see "Execution list" below), so the rest of the list keeps working.

**Where it goes afterwards, and how strong the enemies are, come from the transition data.** At the end the battle builds a `BattleResult` (victory, mining bonus, tokens spent) and loads whatever `BattleSceneTransitionData.CreateReturnData` makes of it: the map passes a function that wraps it in a `MapSceneTransitionData`, or in a challenge sends a defeat to ResultScene as `ChallengeResultTransitionData`. The battle never sees a scene name. Without the function (standalone play) it stays. Skipping the practice battle's tutorial returns a defeat the same way, which the map ignores during the tutorial. `BattleSceneTransitionData.EnemyStrength` (default `EnemyStrength.None`) is applied in `CreateEnemies`: max HP times `HpPercent`, plus a `LayerBoostStatusEffect` of `AttackBonus` when above 0. The battle does not know which mode or layer these come from (see "Challenge mode" in @docs/map-scene.md).

**Debug: forcing the result.** `BattlePhaseDirector.DebugForceFinish(isVictory)` (Editor and Development Builds only, see "Debug features" in the root doc) sets the losing side's HP to 0 (the enemies with `TakePiercingDamage`, since the boss is immune to instant kill; the player with `InstantKill`, which overcharge cannot absorb), then cancels the turn loop even mid-turn — `RunTurnsAbortableAsync` runs `RunTurnsAsync` under a token linked to the scene's, and swallows only its own cancellation. The phase is left at `PlayerExecution` so the hand cannot be used, and the battle then ends the normal way (result toast, `OnBattleFinished`), so the campaign's return to the map and its reward flow run as usual. `BattleSceneInitializer` registers it as **Battle: Win / Battle: Lose** on the 0707 debug panel. `RunTurnsAbortableAsync` itself is in every build (giving up uses it, below); only `DebugForceFinish` is debug-only.

**Giving up.** `BattlePhaseDirector.Surrender()` ends the battle as a defeat through the same abort, without touching HP (so the log shows no "defeated" line); the end reads `_isSurrendered`, toasts 「敗北... 接続を切断した」 and raises `OnBattleFinished(false)`, so the map treats it as an ordinary loss (Backup Boost). It does nothing once the battle is decided (`IsDecided`).

## Battle log (`Window/BattleLog/`, `UseCase/BattleLogRecorder.cs`, `Presenters/BattleLogFeedPresenter.cs`)

What each side did is written into a `BattleLogModel`, shown live at the top centre while actions run, and kept for a **Log** window.

The log's data is in `Common/` (`BattleLogModel`, `BattleLogKind`, `BattleLogEntry` in `Common/Models/BattleLog/`; `BattleLogFormatter`, `BattleLogLine` in `Common/Presenters/BattleLog/`), because the log window's init data carries the model and the formatter. The window itself is `Window/BattleLog/` (presenter, view, `BattleLogRowView`, its Initializer). What only the battle does stays here: `BattleLogRecorder` (it watches the battle's models) and the live feed (`BattleLogFeedPresenter` / `BattleLogFeedView`).

- **Recorded as data, worded at display time.** A `BattleLogEntry` holds the kind (`BattleLogKind`), the units, card, status effect and a number, never text. `BattleLogFormatter` turns it into a `BattleLogLine` using the `UIText` `Log*` format strings, so switching language rewords the whole log. When the same enemy appears twice, it gets A/B suffixes (`トロイの木馬A`).
- **Nothing in the card effects knows about the log.** `BattleLogRecorder` watches every unit's `OnHpChanged` / `OnStatusEffectsChanged` / `OnStatusEffectValuesChanged` and writes the *difference*: damage, heal, status gained / changed / worn off, defeated. Block absorbing a hit changes a value without an event, so it also diffs statuses on every HP change: a hit into 5 block reads "block -5" then "3 damage". Timed effects are logged only when gained and when they wear off, not as their turns tick down. A block used up to 0 is not logged again when it is purged. A new card effect is therefore logged with no change here.
- **Hooks from the flow.** The Initializer connects these to `Record*`:
  - `BattleCommandExecuteUseCase.OnCardExecuting` (user, card, target — player and enemy alike);
  - `BattlePhaseDirector.OnPlayerTurnStarted` / `OnEnemyTurnStarted` (turn headers);
  - `OnUnitTurnEnding` / `OnUnitTurnEnded` — HP changes between them are logged as over-time damage or heal, carrying the status effect that caused them (`UnitStatusModel.LastHpChangeSource`), so the line names it: 「トロイの木馬Aにウイルスで4ダメージ」 (`UiTextKey.LogDamageFrom` / `LogHealFrom`). Only when no effect is known does it fall back to the generic 「継続効果で」 (`LogDamageOverTime` / `LogHealOverTime`);
  - `OnEnemyStunned`.
- **Status effects are explained with their numbers.** After every status gained or increased, the recorder adds a `StatusDetail` entry holding the value *at that moment* (and a timed effect's `Amount`), since the effect instance keeps changing. It is shown one indent deeper and dimmer, worded from the `StatusEffectLogDetail` table (`{0}` value / turns left, `{1}` size): データ破損 → 「2ターンの間、回復がダメージになる」, block → 「攻撃ダメージを5まで防ぐ」. A value dropping to 0 (spent block) gets no detail.
- **Colour by side.** Every entry carries an `Actor`: the card user, or the unit whose turn is ending. Lines are cyan for the player's actions and magenta for the enemies', turn headers yellow. Result lines are indented under their card line. Each line shows the portrait of its subject (`BattleLogRowView`).
- **Live feed** (`BattleLogFeedPresenter` / `BattleLogFeedView`, `Canvas/LogFeed`, drawn just above `CardDetail` in the same spot). It opens on `PlayerExecution` and stays through the enemy turn, starting from the latest turn header. It closes a short moment after the phase returns to `Draw` / `Player`. It shows the newest 7 lines, bottom-aligned, and new lines flicker in. It takes no input.
- **Log window** (`BattleLogWindowPresenter` / `BattleLogWindowView`, `Prefabs/BattleLogWindow.prefab` on BattleScene's `PopupCanvas`, opened by `Canvas/LogButton` bottom-left, a `CyberButton` at 0.7x `localScale` so it reads as a secondary control next to Execute; scale rather than height, because the slanted sliced sprite kinks when stretched vertically). The whole battle's log in a `CommonScrollList` of `BattleLogRowView.prefab` rows. A thin cyan scrollbar on the right (`ScrollRect.verticalScrollbar`, auto-hidden when everything fits) shows that it scrolls, and the viewport's `RectMask2D` has a vertical `softness` so rows fade out at the top and bottom edges instead of being cut. It opens scrolled to the end (`CommonScrollList.ScrollToEnd`) and follows new lines only while already at the end. The Close button or a background click closes it; the battle keeps running underneath.

## Purge, loopback and running out of commands (2026-09-27)

- **Purge pile.** `BattleSceneInitializer` puts a fourth pile, `Purge`, in `BattleCardPilesModel`. A command goes there instead of the archive when its `CardData.PurgeOnUse` is set (`Mining`) or when `Multithread` hit it, and it never comes back to the deck this battle. Its count is `Canvas/PurgeCountView` (a copy of the archive's `CardPileCountView` at 0.75x, right of it, tinted magenta), pushed by `BattleCardPurgePilePresenter` with the label `UiTextKey.PurgePile` (パージ / Purged).
- **Where a command goes.** `BattleCommandExecuteUseCase.ExecuteNext` asks `player.CalculateCommandDestination(PurgeOnUse ? Purge : Discard)` after the effects ran, between `BeginCommand` and `EndCommand` (see "Status effect system" in the root doc). `ReturnToHand` puts it in `BattleCardPilesModel.Returning`, which `BattleDrawUseCase.Draw` moves into the hand **before** drawing, so returned commands count toward the hand size. `Multithread` makes the effects run `CommandRepeat` times, re-aiming at the next enemy if the target dies in between; `OnCardExecuting` (and so the log's "used" line) fires once.
- **The exploit chain is single-use.** A chain step's effect implements `IChainCardEffect` (`StartsChain`, `CompletesChain(user)`). `BattleCommandExecuteUseCase.ExecuteNext` asks before running a command whether it completes the chain (the chain status is gone once it runs), remembers this turn's steps (`CommandHistoryModel.ChainCards`, restarted by step 1, cleared in `BattleTurnEndUseCase.EndPlayerTurn`), and when the chain completes sends the finisher to the purge pile and moves the earlier steps from the archive (or the returning pile, after Loopback) to it, each reported through `OnCardDisposed` so the log shows them. It counts as complete when step 3 runs in order, whether or not the target is immune to the kill. A broken chain goes to the archive as usual (`ExploitChainPurgeTests`).
- **Losing by purge.** `IsDeckExhausted` is true when deck, hand, archive, execution list and the returning pile are all empty and something was purged. The director checks it after every player command; it ends the battle as a defeat (`OnDeckExhausted`, toast 敗北... コマンドがすべてパージされた), unless that last command already defeated every enemy.
- **Log.** `OnCardDisposed` (player commands that did not go to the archive) is logged as `CardPurged` / `CardReturned`, and the director's `OnDeckExhausted` as `DeckExhausted` (`UiTextKey.LogCardPurged`, `LogCardReturned`, `LogDeckExhausted`).
- **Tokens.** The battle gets the player's tokens through `BattleSceneTransitionData.Tokens` (the standalone mock is `BattleSceneInitializer._tokensMock`) and keeps them in a `BattleTokenModel`; a token-cost command (Cloud Burst) pays from it when it is queued (`BattleCommandQueueUseCase`) and gets them back when it returns to the buffer. What was spent goes back in `BattleResult.TokensSpent`, win or lose.
- **Redo and context.** `BattleCommandExecuteUseCase.ExecuteNext` runs a Redo as the previous command (`ExecutePrevious`, re-aimed with `BattleTargetResolver.Resolve`, chain steps skipped) and remembers every other command it runs. Effects that look at the buffer or at every unit get a `CardExecutionContext` built at execution time (see "Card system" in the root doc).
- **Token bonus.** `HandleBattleFinished` sums the player's `TokenBonusStatusEffect` values into `BattleResult.TokenBonusPercent`; the map applies it to a victory's tokens (@docs/map-scene.md).

- **Choosing what to purge (Buffer Overflow).** For a card with `HandPurgeCount > 0`, `SelectTarget` does not queue: it calls `CardSelectionModel.BeginPurgeChoice(card, target, capacity)`, which clears `PendingCard` (the target list closes) and raises `OnPurgeChoiceChanged`. The hand presenter keeps that card lifted, opens `Canvas/PurgePicker` (`BattlePurgePickerView`: `// SELECT PURGE`, the hint, `n/2`, a Confirm `CyberButton`, following the card like the target list) and turns clicks on other buffer commands into toggles (`BattleCardView.SetPurgeMarked`: a magenta `PURGE` overlay, `PurgeMark` in `CardView.prefab`; marked cards lift halfway). Hover does not move the selection meanwhile, nothing is greyed, and a click on empty space cancels. Confirm calls `ConfirmPurgeChoice(cards)` (1..capacity, all in the buffer, not the card itself): the chosen commands leave the buffer with the command, flying to the purge pile, and ride on the `CardCommand` until it executes. Returning the command gives them back; leftovers at the end of the turn go to the archive with it. A card that has nothing else in the buffer to purge is refused ("パージできるバッファがありません").
- **Execute becomes Confirm while choosing.** During the purge choice the Execute button reads 決定 (`UiTextKey.PurgeConfirm`) and does exactly what the panel's Confirm does; it is disabled until at least one command is marked. Both go through the model: the hand presenter reports the marked count (`CardSelectionModel.SetPurgeChosenCount`), `BattleCommandListPresenter` reads `IsChoosingPurge` / `CanConfirmPurge` for the label and `interactable`, and its click calls `RequestPurgeConfirm`, whose `OnPurgeConfirmRequested` the hand presenter handles with the same method as the panel's button. When the choice ends it reads 実行 again.

**Enemy targets.** `ExecuteEnemyTurnAsync` passes the player as the target, except for a card whose `ChoosesAlly` is set (the Botnet's `BotRepair`): that one gets `EnemyPartyModel.FindWeakestLiving()`.

## Enemy intent and glitch (2026-09-29)

- **Intent.** Right after the player's draw, `BattlePhaseDirector.PlanEnemyActions` calls `EnemyData.PickCards()` for every living enemy and stores it on `BattleEnemy.SetPlan` (`PlannedCards`, `OnPlanChanged`). The enemy turn plays exactly that plan and clears it. `EnemyIntentPresenter` shows it in `BattleEnemyIntentView` — the `InfoStack/Intent` rows of `UnitView.prefab`, below the HP bar and above the status effects (`InfoStack` is a static `VerticalLayoutGroup`, so the status list moves up for the player, whose intent stays hidden). Each row (`BattleEnemyIntentSlotView`) reads `0x00 [icon] name`, like the command memory. Actions a stun will skip (the same `CalculateLimit(ActionCount)` cut as the turn) get a dark overlay, re-evaluated whenever the enemy's status effects change. Hovering a row shows the card on the `// COMMAND DATA` panel through `CardPreviewModel`, with one owner token per row.
- **Labels.** Both lists carry a header so they cannot be mistaken for each other: `// 次の行動` / `// NEXT ACTION` over the intent (`UiTextKey.IntentHeader`, inside `Intent`, so it hides with it) and `// 状態効果` / `// STATUS` over the status effects (`UiTextKey.StatusHeader`, first child of `StatusEffectParent`, hidden while there are none).
- **Status effects show their name only.** `StatusEffectView` keeps the description in a `Tooltip` child that opens right above the row while the pointer is on it. The tooltip is outside the row's layout (`ignoreLayout`) and is a nested `Canvas` with `overrideSorting` (re-applied every time it opens, since the override can drop when the canvas is enabled) so it draws over the hand. The prefab is on layer `UI_Default` — a nested canvas on `Default` is culled by the UI camera and silently draws nothing.
- **Status effects applied.** `UnitStatusModel.OnStatusEffectApplied` (new or stacked, with the resulting effect) floats the effect's name and value as text only (`BattleUnitEffectView.PlayStatusText`, yellow, below where numbers start, stacking down when several arrive together). An effect refused by an immunity (`OnStatusEffectBlocked`) floats 「ウイルス 無効」 (`UiTextKey.StatusBlocked`) in grey with the `Error` sound.
- **Glitch.** Before each planned action, the director rolls `CalculateLimit(StatLimitType.GlitchChance, 0)` percent; on a hit it plays `_glitchCard` (the enemy-only `SystemError`, set on `BattleSceneInitializer`) with the enemy as both user and target. It is not shown in the intent, by design.
- **Buffer lock.** `BattleDrawUseCase.Draw` caps the draw with `CalculateLimit(StatLimitType.DrawCap, int.MaxValue)` after the "at least one" rule, so Buffer Overflow's lock can leave the buffer empty. Commands returning by Loopback still enter the buffer.

- **Summoned enemies.** `PlanEnemyActions` hands each enemy an `EnemyPickContext` (HP, living allies, turn number, `BattleEnemy.TurnsAlone`), and `BattleEnemy.CountTurnEnd` updates the turns alone after each enemy's turn. A summoned enemy lives in a reserve slot made at the start (`BattleEnemyFactory.CreateReserves`, placed in a hidden enemy view by `CreateEnemies`) and is brought back by `EnemyPartyModel.Summon`; `EnemySummonPresenter` shows the view and plays `MemoryWrite`, `UnitPresenter` redraws it on `UnitStatusModel.OnRevived`, and `BattleLogRecorder` only resets its snapshot. Summoned during the boss's turn, it has no plan until the next player turn. See "Boss" in the root doc.

## Pacing and battle speed

Every wait in `BattlePhaseDirector` is a base time in milliseconds, divided by `GameSettingsRepository.BattleSpeed` (1 = normal, clamped 0.5–3, handed in as a `Func<float>`):

| Wait | Base |
| --- | --- |
| each player card | 900 ms |
| each enemy action | 1100 ms |
| an enemy's last action → its turn-end effects (virus, worm, regeneration…), only when it has a status effect | 700 ms |
| between enemies | 400 ms |
| player turn → enemy turn | 500 ms |
| after the player's last card | 700 ms |
| battle end | 1500 ms |

The gaps exist so each action can be followed in the log and on screen. Until an options screen exists, the debug panel's **Battle: Speed %** changes the setting.

## Battle menu (the shared `Window/Menu/`, `Prefabs/MenuWindow.prefab`)

`Canvas/MenuButton` (bottom-left, just above Log; it used to be the Options button, and `BattleSceneViewContainer` keeps its reference through `FormerlySerializedAs`) opens the shared menu window (generated under `PopupCanvas`, `MenuWindowView` / `MenuWindowPresenter`, see "Button-list windows" in the root doc) with **オプション** and **あきらめる** (magenta, `MenuItemStyle.Danger`, as an irreversible action). The Initializer only builds its `MenuWindowInitData`. It is a window like the map's Menu: it blurs the screen behind it, and the battle keeps running underneath, as with the log window. The Close button or a background click closes it.

- **オプション** opens the options window over the menu (`GameOptionsPresenter.Open`); the menu stays behind it.
- **あきらめる** asks through the shared `ConfirmDialog` (「あきらめますか？」, detail 「この戦闘は敗北になり、バックアップブーストを受けます」, OK あきらめる, Cancel 戻る); OK closes the menu and calls `BattlePhaseDirector.Surrender`. Its `canPress` is `!IsDecided`: the button is greyed out once the battle is decided, and OK does nothing if the battle was decided while the dialog was open (a win is never turned into a loss).
- **One confirm dialog, several users.** The options window's "discard changes?" and the tutorial's skip use the same dialog, a `WindowHandler<ConfirmShowData>`; each question gets its answer through its own `ConfirmShowData` callbacks.

Until 2026-10-06 the menu was a small battle-only panel (`BattleMenuPresenter` / `BattleMenuView`, `Canvas/BattleMenu`) that opened above the button without blur; it was replaced by the shared menu window at the user's request.

## Options (`Common/Presenters/GameOptionsPresenter.cs`, `Prefabs/GameOptionsWindow.prefab`)

The same options window as the title (see "Options" in @docs/title-scene.md): BGM and SE volume, battle speed, language and display mode, with Reset to Default / Cancel / Apply. Deleting user data is the title's only and is hidden here: the battle builds `GameOptionsPresenter` without `onDeleteUserData`, so the row is hidden and the window is one row shorter. It opens from **オプション** in the battle menu (`openButton: MenuView.OptionsButton`); the battle keeps running underneath, like the log window. A new battle speed takes effect from the next wait, volumes at once (they are heard while dragging), and a new language rewords everything on screen, the battle log included, through each presenter's `OnLocaleChanged`.

It replaced the battle-only `BattleOptionsPresenter` / `BattleOptionsModel` / `BattleOptionsWindowView` / `BattleOptionsWindow.prefab` (battle speed only) on 2026-10-01. The confirm dialog is shared with Give Up (`WindowHandler<ConfirmShowData>`; each question is answered through its own show data). Both the options window and the confirm dialog are generated at start-up (`WindowUseCase`, see "Windows are generated, not placed" in the root doc) rather than placed in the scene.

## Card play flow

Playing a card (changed 2026-09-29): **click** a card in hand and it goes straight into the **execution list** (`BattleCommandQueueUseCase.TryPlayWithoutChoosing(card, preferFrontTarget: true)`). A card with nothing to choose — it acts on the player, hits every enemy, or only one enemy is alive — uses that target (`FindAutoTarget`); a card that aims at one of several living enemies goes to the **priority target** (below). A purge command goes on to its purge choice. To aim at another enemy, **hover** the card: after the dwell, a card that needs a choice opens the `// SELECT TARGET` panel above it (`TrySelectCard`), and picking there queues it. Clicking the card while the panel is open still queues it on the priority target. Then press Execute to run the list from the front and end the turn. Earlier every card went through target selection so that playing had one gesture; the extra click on self-cards turned out not to be worth it.

**Touch: tap twice** (2026-10-17). How hand input is read is a strategy, `IHandInteraction` (`Presenters/CardPile/HandInteraction/`), picked in the Initializer from `Common/Interaction/InteractionModeDetector.Current` (`UnityEngine.Device.Application.isMobilePlatform`, decided at run time rather than by `#if UNITY_ANDROID`. It must be the `Device` one: the Device Simulator only overrides that, and `UnityEngine.Application.isMobilePlatform` stays false in the Editor. **Tools > Interaction > Force Touch Mode** forces the touch version in the Editor, mouse clicks standing in for taps; it applies from the next battle). `BattleCardHandPilePresenter` keeps the operations (play, select, inspect, purge marks, preview) behind `IHandOperations`; the strategy only decides which input calls which.

- `PointerHandInteraction` is everything described in this section: lift on enter, the target panel after the dwell, click to play, release after leaving.
- `TouchHandInteraction` ignores pointer enter/exit (touch sends enter on press and exit on release, which would hide the details and trigger the leave release). The **first tap** lifts the card, opening the target panel when it needs a choice; **tapping the lifted card again** plays it (on the priority target, or explains why it cannot). A target option tap picks that enemy, an empty-space tap puts the card back. Purge marks are toggled by single taps as before.

**Touch: a tap pins the description.** In touch mode `CardPreviewModel.Owner` is "the one thing whose description is open", and it changes only when something else is tapped — not when the command is played or empty space is tapped. The one exception is pressing Execute: `BattleCommandListPresenter` clears it (`CardPreviewModel.Clear`) when the phase becomes `PlayerExecution`, so the description does not cover the results. Every source writes it on tap and never hides it: hand cards (in any phase), queued commands, an enemy's next-action rows (`BattleEnemyIntentSlotView.OnClicked`) and status effects. A status effect has no card, so `StatusEffectTapPresenter` (touch only, one per unit view) writes its row as an owner with a null card, which closes the details panel (`BattleCardDetailPresenter` hides when there is an owner but no card) and opens that row's tooltip (`BattleUnitStatusView.SetExpandedStatusEffect`, hover expansion off). A queued command's first tap pins it, shows its move arrows (`BattleCommandCardView.SetPinned`, hover off) and highlights its target; the second tap returns it to the buffer.

**Priority target** (2026-10-04). `PriorityTargetModel` (`Models/`) holds the enemy the player chose; `Current` is that enemy while it lives, otherwise the front-most living one (so it starts on the front enemy). Clicking an enemy unit while no target is being picked chooses it: the Initializer wires each enemy's `onTargetClicked` to `SelectTarget` first and, when that refuses (nothing pending), to `PriorityTargetModel.Select`. `BattleTargetResolver` reads it through `getPriorityOpponent` (`FindFrontOpponent`). `PriorityTargetPresenter` shows `BattlePriorityTargetView` (`PriorityMarker` in `UnitView.prefab`: a yellow down-pointing `ui_cursor` and a decorative `TARGET` between the name and the head, opening from a line and bobbing in 2 px steps) on that enemy only and turns its name yellow (`BattleUnitStatusView.SetPriorityTarget`), only while two or more enemies are alive; a choice plays `CardSelect`. When the chosen enemy dies the marker moves to the front-most living enemy on the next HP change.

Dragging a card onto a unit was the earlier mechanism and is **gone**. `BattleCardView` has no drag handlers, `UnitPresenter` no longer hit-tests screen points, `CardDropCandidate` / `RegisterDropTarget` / `ClearDropTargets` are deleted, and with them the last use of the UI camera — which is why `BattleSceneViewContainer` no longer exposes the `Canvas` at all. If a future scene needs screen-point hit testing again, note what the old code got right: it passed `_viewContainer.Canvas.worldCamera`, never `Camera.main` and never `null`, because this project's Canvas is `Screen Space - Camera`.

The flow, end to end:

1. **`BattleCardView`** (`Views/BattleCardView.cs`, `CardView : MonoBehaviour` base in `Common/Views/` + this subclass implementing the pointer click/enter/exit handlers) forwards input and nothing else: `Initialize(cardData, onClicked, onHovered)` stores two plain `Action`s. `OnPointerClick` invokes the first. The second fires once the pointer has **rested on the card for `_hoverDwell` (0.1 s)** — the dwell is what lets the player move the pointer up to the target list above the selected card without selecting a neighbour they brush past. It passes no argument on purpose — the presenter builds one callback per view, so *which* view was clicked is already baked into the callback. It knows nothing about phases, stamina or targets — it doesn't even know whether the click was accepted.
2. **`BattleCardHandPilePresenter`** is the phase gate: outside `BattlePhase.Player` input is dropped.
   - **Unplayable cards are greyed out.** During `BattlePhase.Player`, every hand card whose `CanSelectCard` is false gets a card-shaped dark overlay (`DisabledOverlay`); if the reason is memory (`CanAfford` false) its cost number also turns magenta, which tells "not enough memory" apart from "execution list full". `RefreshPlayable` re-runs on every hand sync, stamina change, command-list change and phase change. Outside the player's phase nothing is greyed, since nothing can be selected then anyway.
   - **Hover** (`HandleCardHovered`) selects a playable card that needs a choice (opening the panel); any other card is only **inspected** (`_inspectedCardView`): it lifts, with no glow and no target list, and drops again when the pointer leaves. No toast on hover. The lift happens the moment the pointer enters (`HandleHoverChanged`); only opening the panel waits for the dwell, so sweeping across the buffer keeps up. `CardView.prefab` has a transparent `LiftHitArea` below the card, as tall as the lift, so a lifted card still owns its original slot and does not bob up and down at its bottom edge.
   - **Click** (`HandleCardClicked`) plays the card as above; a refusal shows its reason as a toast. That is how the player finds out *why* a card will not play.
   - **Leaving releases the selection.** While a target is being chosen, the selection is kept only while the pointer is on the selected card or on the target panel (`BattleTargetPickerView.OnPointerOverChanged`); once it is on neither for `LeaveGraceMs` (180 ms, enough to cross the gap between them) the selection is cancelled. A click on empty space (`BattleCancelAreaView`) also cancels. Because of this, clicking a unit on the battlefield is no longer a practical way to pick the target; the panel is.
   - **A refused click** shows the reason as a toast (as before) and inspects that card, the same state hovering would have produced. A click on empty space clears both the selection and the inspected card.
   - **Which copy.** `CardData` is a shared asset reference, so two copies of the same card in hand are the same object, and only the presenter knows which one was pointed at. That is why each hand view is handed its own closures at creation.
3. **`BattleCommandQueueUseCase.TrySelectCard`** holds every remaining rule about whether the click is accepted:
   - the execution list being full, or the card costing more stamina than the player has left, shows a `MessageUseCase` toast and refuses;
   - anything else is accepted: the card goes into `CardSelectionModel` and the flow waits for a unit to be picked. Nothing is queued and no stamina is spent yet.
4. **Target selection** goes back the other way: `BattleUnitTargetView` (on the unit's `TargetArea` child) forwards `OnPointerClick` to `BattleUnitStatusView.OnTargetClicked`, which `UnitPresenter` subscribes to and reports through the injected `Action<UnitStatusModel>` — wired in the Initializer to `BattleCommandQueueUseCase.SelectTarget`. `SelectTarget` no-ops when nothing is pending **or when that unit is not a legal target for the pending card**, so a click on the wrong unit — or on any unit at any other time — is harmless. Which side is legal comes from `CardData.TargetsOpponent` (see "Card system" in the root doc) compared against "is this the player's own model", plus "is it still alive" — so with several enemies on screen a card that targets opponents highlights all of the living ones and lets the player pick any of them, while a defeated one is neither highlighted nor clickable. Both the acceptance and the highlight ask the same method, `BattleCommandQueueUseCase.CanSelectTarget`, so what looks clickable and what actually is can't drift apart. `UnitPresenter` does **not** call the use case type directly; it holds a `Func<UnitStatusModel, bool>` and an `Action<UnitStatusModel>` and only reports facts about its own unit.
5. **Stamina is paid when the card is queued, not when it is executed** — so `TrySelectCard`'s "can you afford it" check needs no knowledge of what is already in the list, and the stamina display updates the moment a card is stacked. `ReturnCommandToHand` refunds it (as `StaminaChangeType.Gain`) when a queued card is clicked back out.

**Picking a target without travelling to the unit.** While a card is pending, `BattleTargetPickerPresenter` opens a small `// SELECT TARGET` panel (`BattleTargetPickerView`) right above the selected hand card, listing every unit that card may target. Each option (`TargetOptionView.prefab`) shows the unit's portrait and HP. Clicking an option goes to the same `SelectTarget` as clicking the unit, and which units are listed comes from the same `CanSelectTarget`, so the two paths cannot disagree. The panel exists because the units are far from the hand; clicking the unit on the battlefield still works.

- **Inputs.** The presenter is handed a fixed list of `BattleTargetCandidate` (unit + portrait, built by the Initializer in screen order: player, then enemies front to back). The selected card comes through a `Func<RectTransform>` wired to `BattleCardHandPilePresenter.PendingCardTransform`, so the two presenters never reference each other.
- **Position.** The view is handed the `Func` itself, not a transform, and re-asks it every `LateUpdate`. It follows the card while it lifts or slides, and it moves (reopening) when the player switches to **another copy of the same card**. That switch changes the pending view but not `CardSelectionModel.PendingCard` (the same `CardData`), so no event is raised for it — polling the anchor is what catches it.

**Pointing at a unit (`TargetFocusModel`).** Two things can "point" at a unit: hovering an option in the target list, and hovering a card already in the execution list (its `CardCommand.Target`). Both write `TargetFocusModel`, and every `UnitPresenter` reads it and switches its `BattleUnitTargetView` to the focus colour (yellow, faster pulse) — whether or not a card is pending, since a queued card is hovered outside target selection. `Unfocus(target)` only clears if that unit is the one focused, so moving straight from one option to the next is not undone by the old option's late exit event. Views report the exit when they are disabled or start exiting, so a closed list or a consumed card cannot leave a unit highlighted. The model is separate from `CardSelectionModel` because focus is not part of selecting a card.

**Card details on hover (`CardPreviewModel`, `BattleCardDetailPresenter`).** Hovering any hand card (playable or not, in any phase) or any card in the execution list shows its illustration, cost, name and effect text in large type on the `// COMMAND DATA` panel (`CardDetailView : CardView`, in `Common/Views/` since the card shop's result window uses it too) in the free space at the top centre.

- **Writers.** The hand and command-list presenters write `CardPreviewModel.Show(owner, card)` / `Hide(owner)` from their views' hover callbacks. The hand card reports hover changes **immediately**; only the hover-to-select waits for the dwell.
- **Owner token.** The model keeps who is showing. The owner is the hand view or the `CardCommand` — an opaque token, since copies of one card share a `CardData` — so a late exit from the card the pointer just left cannot hide the one it moved onto.
- **Fallback.** When nothing is hovered, the panel keeps showing the pending card, so its effect stays readable while the pointer travels to the target list.
- **No input.** The panel receives no input.
- **Switching swaps the content in place.** The panel only opens from a line (y-scale) when it appears from hidden; pointing at another card while it is up just replaces the content, with the frame and header still. (A top-down "screen refresh" wipe was tried for switches and dropped.)
- **Closing waits a moment.** `Hide` waits `_hideDelay` (0.12 s) before closing. Moving between cards arrives as "exit old, then enter new" (also when crossing the gap between cards), and closing immediately made the panel blink shut and reopen on every move.
- **Timing.** Time is unscaled and capped per frame.

**Draw order.** `CardDetail` is drawn just before `HandParent`; `HandParent` is the Canvas's second-to-last child, drawn above the command tray so a lifted card never slips under it; `TargetPicker` is last, above the hand.

Feedback for the two states that would otherwise be invisible: the card waiting for a target is raised by `SelectedCardOffsetY` in the hand row, and every targetable unit switches to `BattleUnitTargetView`'s selectable color for as long as a card is pending. The raised card is tracked as a **view**, not as a `CardData` — comparing against `CardSelectionModel.PendingCard` would raise every copy of that card in hand — and `BattleHandLayout.Reposition` re-runs both on click and on `CardSelectionModel.OnPendingCardChanged` (which is what clears the highlight when the card is queued, or when the turn ends). Because both the hand and the units read the same `CardSelectionModel`, neither presenter has to know the other exists.

When hand-size effects push the row past `MaxRowWidth` (1220, what five cards need), the step between cards shrinks so they overlap instead of running into the memory gauge or the Execute button. The memory gauge does the same for its cells: `SegmentGaugeView` shrinks cells and gaps to fit `_segmentParent`'s width, which is why `PlayerStamina/Gauge` has a width (268) but zero height — its pivot is at the bottom, so giving it a height would lift the cells.

**Hand layout is entirely script-driven — there is no `HorizontalLayoutGroup` on `HandParent`.** `BattleHandLayout.Reposition` (`Presenters/CardPile/BattleHandLayout.cs`, owned by `BattleCardHandPilePresenter`) computes a centered horizontal row (`CardSpacing` constant + the prefab's own `rect.width` times its `localScale` — `CardView.prefab`'s root is scaled to `0.85` so a full hand fits under the command tray) and hands each `BattleCardView` its target through `MoveTo` / `PlayEnter`, called from `Sync()` (every pile change) and from the pending-card change above. `BattleCardMotionView` (see "Card motion" in @docs/art.md) moves the card there — it owns `anchoredPosition` from then on, and the presenter only ever supplies targets. This was a deliberate choice over a Layout Group: a Layout Group actively fights any code (or tween/animation) that tries to set a child's position outside of a layout rebuild, whereas script-set positions compose cleanly with animation — which is exactly what the card motion now relies on. If you're tempted to add a Layout Group back for a new panel, consider whether that panel will ever need animated repositioning first — if yes, follow this pattern instead. `BattleCommandListPresenter` lays the execution list out the same way, for the same reason, with one difference: it spaces `CardCommandModel.MaxCount` slots and fills them **from the left** instead of re-centering as the list grows, so each queued card sits on the numbered frame (`CommandTray/Slot1..3` in the scene) that matches its execution order.

**Buffer label.** `Canvas/BufferLabel` (`UiTextKey.BufferLabel`, バッファ / Buffer) captions the hand row from below; the hand presenter pushes it in `Sync`.

**Empty buffer.** When it is the player's phase, the buffer is empty and nothing is queued, `Canvas/BufferEmpty` (`BattleBufferEmptyView`, drawn just under `HandParent`, takes no input) fills the hand's place with `// BUFFER EMPTY`, the reason and what to do: 「バッファロック中のため、このターンはコマンドを読み込めません」 when the player has a `BufferLockStatusEffect` (`UiTextKey.BufferEmptyLocked`), otherwise 「バッファに読み込めるコマンドがありません」 (`BufferEmpty`), and the hint 「実行を押してターンを終了します」 (`BufferEmptyHint`). It opens from a line with a flicker and the hint pulses. `BattleBufferEmptyPresenter` decides it ( on every hand sync, command-list, phase and status change). A buffer emptied by queueing every command shows nothing, since the reason is on screen.

**Stacking order.** When the row overlaps, `BattleHandLayout.Reposition` re-orders the hand's siblings left to right (a card to the right is drawn over the one to its left), then brings the lifted card — the pending one, else the inspected one — to the front.

`BattleCardView`'s prefab anchor/pivot must stay centered (`(0.5, 0.5)` for both `anchorMin`/`anchorMax`/`pivot`) — `BattleHandLayout.Reposition`'s math assumes the card's pivot is its visual center. The same applies to `CommandCardView.prefab`.

## Execution list (`Models/CardCommandModel.cs`, `Presenters/BattleCommandListPresenter.cs`, `Views/BattleCommandCardView.cs`)

`CardCommandModel` is the ordered list of cards waiting to be played, capped at `BattleConstants.MaxCommandCount` (3), holding `CardCommand { Card, Target }` (`Data/CardCommand.cs`). `Target` is never null — a self-acting card is queued with the player's own unit, because the player picked it, so `BattleCommandExecuteUseCase.ExecuteNext` can run every command the same way.

It is a separate model rather than a fourth `CardPileModel` because two things differ: it has a maximum size, and its **order is the thing being edited**. For the same reason it exposes a single `OnChanged` event rather than `CardPileModel`'s add/remove/clear trio — every consumer redraws the whole row anyway, and "reordered" has no per-card event to fire. `RemoveAt` returns `null` for an out-of-range index and `Swap` ignores one, which is what lets callers skip bounds checks (the director's "execute until the list is empty" loop and the edge cards' one-directional arrows both rely on this).

`BattleCommandListPresenter` owns the whole command area, **including the Execute button** — the button is part of that UI rather than a thing of its own, so it is wired here (`onClick` → `RequestExecuteCommands`, `interactable` → phase) instead of in the Initializer. `Sync` keeps one pooled `BattleCommandCardView` per **`CardCommand` instance** (a new instance is created per queue, so two copies of the same card are still told apart) under `BattleSceneViewContainer.CommandListParent`. A view therefore travels with its command: a reorder or the close-up after an execution calls `MoveToSlot`, which slides the view to its new address and replays the write scan ("rewrite"). A command that leaves plays an exit chosen from why it left:

- **Return** (the player clicked it back) drops toward the hand. This is remembered in `_returningCommand`.
- **Execute** (it left during `PlayerExecution`) flashes, collapses and rises away.
- **Discard** (any other time, i.e. end-of-turn leftovers) flies to the discard pile.

It also re-hands each view its callbacks on every sync, because a card's index — and therefore what "move left" means for it — changes as the list is reordered. It also pushes the Execute button's label through `LocalizationHelper.GetUiText(UiTextKey.Execute)`, which is why its `OnLocaleChanged` re-runs `Sync`.

`BattleCommandCardView : CardView` shows the arrows only while hovered (`IPointerEnterHandler`/`IPointerExitHandler`) and only on the side that has a neighbour (`SetMovable(canMoveLeft, canMoveRight)`). Two details keep that working:

- The arrow buttons are **children of the card and sit inside its rect**. uGUI's pointer enter/exit walks up the hierarchy, so moving the cursor onto a child button does not raise `OnPointerExit` on the card — the arrows don't vanish from under the cursor.
- Clicking the card body returns it to the hand, and clicking an arrow does not, because uGUI dispatches a click to the *nearest* `IPointerClickHandler` above the raycast hit: the button consumes its own clicks.

`CommandCardView.prefab` is `CardView.prefab` plus the two arrow buttons, with its root scaled to `0.6` so the list fits between the hand and the units. `BattleCommandListPresenter.SlotPosition` multiplies the prefab's `rect.width` by that `localScale`, so changing the scale in the prefab is enough — don't also adjust the spacing math.

## Card pile presenters (`Presenters/CardPile/`)

`CardPilePresenterBase` (a `Common/Presenters/PresenterBase.cs` subclass) is the shared base for all three pile presenters: constructor only stores the `CardPileModel` (exposed to subclasses as the `protected readonly Pile` field — deliberately not named `CardPileModel` to avoid shadowing the type of the same name), `OnInitialize()` subscribes to `Pile`'s three events and does the first `Sync`, `OnDispose()` unsubscribes. It also implements `OnLocaleChanged()` as `Sync(Pile)` and `sealed`s it — a pile presenter's answer to a locale change is always "re-run `Sync`", so the three concrete pile presenters implement nothing for it. `BattleCardHandPilePresenter` implements `Sync` as a **diff**, not an index-by-index rebind: it walks the new hand against its current views in order and matches views to cards by `CardData`. Only the views that lost their card play an exit, and only the new cards get fresh views (from a pool — views are never destroyed, just `SetActive` toggled). Rebinding by index would make the *last* view vanish whenever a card left the middle of the hand.

- **Duplicate cards.** The model has to drop the same copy the player clicked, or the view diff (which keeps views in model order) sends the *other* copy flying: the presenter passes the clicked view's index (`_cardViews` is kept in model order) into `TryPlayWithoutChoosing` / `TrySelectCard` / `ConfirmPurgeChoice`, `CardSelectionModel.PendingHandIndex` carries it through target and purge selection, and `AddCommand` removes by position with `CardPileModel.RemoveCardAt` (back to front, falling back to `RemoveCard` when no index is known). On the view side, `CardData` is shared, so two copies of a card cannot be told apart by data. The view that was just deselected (`_releasedCardView`, captured in the pending-card-cleared handler, which fires right before the queued card is removed) is avoided when matching, so the card the player actually picked is the one that leaves.
- **Direction** is read from the phase. Cards removed in `Player` were queued (Upload, toward the command list); otherwise they were discarded. Cards added in `Player` came back from the command list; otherwise they were drawn from the deck.
- **Stagger.** Consecutive enters and exits are staggered across `Sync` calls, because a draw or discard arrives as one event per card.

It then repositions (see above); it also overrides `OnInitialize`/`OnDispose` to subscribe to `CardSelectionModel` on top of the base's pile events. `BattleCardDeckPilePresenter`/`BattleCardDiscardPilePresenter` implement `Sync` by just pushing `cardPileModel.Count` into a `CardPileCountView` (from `Common/Views/`) — no per-card views for those two piles.

## Unit status display (`Presenters/UnitPresenter.cs`, `Views/BattleUnitStatusView.cs`)

One `UnitPresenter` per unit — the player plus one per entry in `BattleSceneViewContainer.EnemyStatusViews` — constructed with that unit's `UnitStatusModel`, its `BattleUnitStatusView`, the shared `CardSelectionModel`, a `showStamina` bool and an `onTargetClicked` callback. `Initialize()` calls `view.SetStaminaActive(showStamina)` once (the Initializer passes `true` for the player, `false` for the enemy — stamina is the player's own resource, showing it on the enemy has no meaning) and does the first HP/stamina sync; `BattleUnitStatusView.SetStamina` itself also checks `_staminaParent.activeSelf` so a stray call while hidden is a no-op. The player's stamina is shown bottom-left next to the hand (`Canvas/PlayerStamina`), not on the unit: the player's `_staminaParent`/`_staminaText` point there, and the unit prefab's own `Stamina` child is a disabled stub that only exists so the enemies' views have something to hide.

`canBeTargeted` is asked on every `CardSelectionModel.OnPendingCardChanged` and decides the highlight; `onTargetClicked` reports the click. Both are plain delegates rather than a `BattleCommandQueueUseCase` reference, and every unit gets the same pair — a unit's presenter knows nothing about sides or about how many other units exist, which is why going from one enemy to two needed no change in this class at all.

An enemy's name (`EnemyName` table, `LocalizationHelper.GetEnemyName`) is shown above its portrait (`NameText` in `UnitView.prefab`); `UnitPresenter` takes the `EnemyData` for that and re-reads the name on a locale change, and the player passes `null`, which hides the label.

`BattleUnitStatusView` is a single `sealed` class (not split into a generic base + scene subclass) — HP/stamina text, `_staminaParent` and `_targetView` all live directly on it, because nothing outside BattleScene has needed the plain-display-only version. `_targetView` points at a `BattleUnitTargetView` on a child object (`TargetArea`), independently assignable in the Inspector, so the clickable area can be a sprite-shaped child rather than the whole status panel. That component keeps its `Graphic` for two jobs at once — it is both the raycast target and the "you can pick me" highlight — so don't disable the `Graphic` to hide it; make it transparent instead, or the unit stops being clickable. If a future scene needs a unit status display without the targeting concept, that's the point to reconsider splitting it (see "View" in the root doc's Layering section) — don't split preemptively before that's actually true.

**Block is shown as a barrier (`Views/BattleBlockBarrierView.cs`, `Barrier` in `UnitView.prefab`).**

An energy wall sits in front of the portrait (behind `TargetArea`, so clicks still reach the target), with the block value on a badge.

| Change | What the wall does |
| --- | --- |
| Gaining block | opens from a line and flashes |
| Stacking more | pulses |
| Absorbing a hit | shakes and sprays shards; three crack overlays appear as the value falls below 3/4, 1/2 and 1/4 of the peak since it was raised, and the wall thins |
| Reaching 0 | shatters (a big shard burst while it collapses sideways) |

`UnitPresenter` sums the unit's `BlockStatusEffect` values and pushes them on `OnHpChanged` (absorption), `OnStatusEffectsChanged` (gained/expired) and `OnStatusEffectValuesChanged` (stacked). The view decides the animation from whether the value went up or down, and knows nothing about how block works.

## Command use cases (`UseCase/`)

What the player does with commands is split by **who calls it**, into four use cases that hold no state of their own: everything that lasts lives in models, and `BattleSceneInitializer` hands each use case only the models it needs. Until 2026-10-08 all of this was one `BattleCommandUseCase` (with `BattleCommandExecutor` and `BattleTokenWallet` inside it), kept whole because selecting and executing touched the same models; it was split at the user's request once its non-model state (the returning pile, the chain and Redo memory, the tokens) had moved into models.

| Use case | Called by | Does |
| --- | --- | --- |
| `BattleDrawUseCase` | the director | `Draw()` at the start of the player's turn |
| `BattleCommandQueueUseCase` | the hand and command-list presenters, the unit and target-list clicks | choosing a card, its target and what to purge, queueing, returning, reordering, `RequestExecuteCommands()` |
| `BattleCommandExecuteUseCase` | the director | `ExecuteNext()`, `ExecuteEnemyCard()`, `IsDeckExhausted`; raises `OnCardExecuting` / `OnCardDisposed` (the log, `BattleActionPresenter`) |
| `BattleTurnEndUseCase` | the director | `EndPlayerTurn()` |

The models they share:

- `BattleCardPilesModel` — deck, hand, discard, purge and `Returning` (Loopback's commands for the next buffer, never shown), plus `PileOf(destination)` and `HasOnlyPurged`.
- `BattleTokenModel` — the tokens a battle may spend: pay when queued, refund on return, what was spent (`BattleResult.TokensSpent`).
- `CommandHistoryModel` — this turn's exploit-chain steps and the last non-Redo command (card, target, purge count) Redo repeats; `BattleTurnEndUseCase` forgets both.
- `CardCommandModel.OnExecuteRequested` — the Execute button's request, on the model so that the queue use case and the director never reference each other.

`BattleTargetResolver` (`UseCase/`, `BattleTargetResolverTests`) is the one helper the queue and execute use cases share: the automatic target, the priority / front opponent, whether a unit is a legal target, re-aiming a defeated one (`Resolve`), and every living unit, player first. It holds no enemy state: the roster is read through `Func`s (`EnemyPartyModel.FindNextLivingTarget`, `GetLivingStatuses`, `PriorityTargetModel.Current`), so tests hand it two-line stubs. No use case holds the enemy's `UnitStatusModel` or the director.

**Queue** (`BattleCommandQueueUseCase`). Selecting a card and queueing it stay in one class because they share the refusal check (memory, list full, tokens, nothing to purge) and the payment made when a command is queued.

- `TrySelectCard(CardData)` — enters target selection; all the rules listed under "Card play flow" above, showing a toast with the reason when it refuses.
- `TryPlayWithoutChoosing(CardData, preferFrontTarget)` — the hand-click entry point: queues on the only possible target or the priority target, or answers `NeedsTarget`.
- `CanSelectCard(CardData)` — the same check without the toast, for selecting on hover. Both go through one private `GetSelectRefusal`, so they cannot disagree.
- `CanSelectTarget(UnitStatusModel)` — can the pending card be aimed at that unit? `false` when nothing is pending. The presenter's highlight and `SelectTarget` both go through it.
- `SelectTarget(UnitStatusModel)` — the unit-click entry point. Queues the pending card against that unit; returns `false` and does nothing when nothing is pending or the unit is the wrong side.
- `ConfirmPurgeChoice(cards)`, `CancelSelection()`, `ReturnCommandToHand(int index)` (refunds memory and tokens and gives back the commands set aside to purge), `SwapCommands(int, int)`.
- `RequestExecuteCommands()` — the Execute button; clears any pending selection and raises `CardCommandModel.OnExecuteRequested` for the director. It does not execute anything itself, because the pacing belongs to the director.

**Execute** (`BattleCommandExecuteUseCase`).

- `ExecuteNext()` — runs the front of the list and returns `false` when the list is empty: purges the commands set aside, repeats for Multithread, runs Redo as the previous command, tracks the exploit chain and sends the command where `CalculateCommandDestination` says. No stamina is taken here — it was paid when the card was queued. Before running the effects it re-checks the target: if it died since being picked, `BattleTargetResolver.Resolve` re-aims it at the next living enemy (front to back, wrapping); with none left the original target is used — harmless, because the director stops the list on `AreAllDefeated` anyway.
- `ExecuteEnemyCard(CardData cardData, UnitStatusModel user, UnitStatusModel target)` — takes **both** units explicitly, because no use case holds the enemy's model or its cards. It only runs the card's effects: an enemy has no hand/deck/discard and no stamina, so **neither the card nor any cost is consumed** and no pile is touched. How often the enemy may act is `EnemyData`'s business, not this method's.
- `IsDeckExhausted` — nothing is left anywhere but the purge pile (and the list is empty); the director then ends the battle as a defeat.

**Draw and turn end.** `BattleDrawUseCase.Draw()` moves `Returning` into the hand first, then draws up to `BattleConstants.MaxHandSize` run through the player's `CalculateLimit(StatLimitType.HandSize, …)`, never fewer than 1, capped by `DrawCap`, reshuffling discard into deck when the deck runs out. `BattleTurnEndUseCase.EndPlayerTurn()` clears the selection and this turn's history, discards anything still in the execution list (normally nothing), discards the hand and restores the player's stamina. It raises no event: the director calls it, rather than being told by it.

**Tests** build all four the way the Initializer does through `Tests/EditMode/BattleCommandRig.cs` (`rig.Queue.TrySelectCard`, `rig.Execute.ExecuteNext`, …), since one test usually draws, queues, executes and ends a turn in a row.

## Screen layout and visuals

The layout follows the usual HIG principles plus the conventions card games have trained players on, so decisions can be checked against a reason rather than taste:

- **Top: the battlefield.** Player on the left facing right, enemies on the right (mirrored with a `-1` x-scale on `Portrait`). Each unit reads top-down: portrait → HP bar → status effects. Units are instances of `UnitView.prefab`, which holds **all** of their visuals and effects; an instance overrides only its position, its portrait sprite and that mirroring. Change the look in the prefab, not per instance.
- **Middle: the execution list**, drawn as an instruction-memory board (`CommandTray`) with sockets addressed `0x00`–`0x02` — capacity and order are visible before the first card is queued. A queued card is shown being "written" into its socket (`BattleCommandWriteEffectView`), and command cards show only name and illustration, because their description would be unreadable at 0.6x.
- **Bottom: the hand**, centred. Stamina — shown to the player as **メモリー残量 (memory remaining)**, a `SegmentGaugeView` of memory-chip cells plus `n/max`, since cards are instructions loaded into memory — sits bottom-left above the deck, which is labelled **コマンドデッキ / COMMAND DECK** (the discard pile is **アーカイブ / ARCHIVE**; both are `UIText` values, the keys are still `DeckPile` / `DiscardPile`); the Execute button (the primary action, the biggest and most saturated control) sits bottom-right above the discard pile, where card games put "end turn".
- The screen is dark, so text is light (`#E8FBFF`). Dark `INK` text only goes on neon fills (the card name band). The Execute button is a translucent, slanted cyan panel with light italic text, and ripples on hover and click (`ButtonRippleEffect`, see @docs/art.md). The HP numbers sit above the bar rather than on it, so they never land on the lime fill.

Where each image comes from and how to replace it is in @docs/art.md. HP changes are played by `BattleUnitEffectView` (shake, alpha blink, floating number, particle burst), fed by `UnitPresenter` with the delta from the last HP it displayed and **its cause**, shown on a small dark tag under the number (a tag rather than an outline, because the Japanese glyphs live on the font's second atlas, which does not inherit an outline material). The cause is the status effect whose turn hook made the change (`UnitStatusModel.LastHpChangeSource`: virus, worm, regeneration), otherwise the command being executed (`CurrentActionModel`, written by `BattleActionPresenter` from `OnCardExecuting` and cleared at turn starts and turn-end effects); a heal turned into damage appends the reversal's name (「リペアパケット（データ破損）」). The same place plays `Hit` / `VirusTick` / `Heal`; `BattleUnitStatusView.SetDefeated` greys out a unit at 0 HP. `BattleUnitTargetView` pulses its selectable colour so a pickable unit reads as clickable.

**Animated units (`Presenters/UnitVisualPresenter.cs`).** One per unit, built after the `UnitPresenter`s and before the target list (so the list picks up the visual's icon). `Initialize` calls `BattleUnitStatusView.ApplyVisual(definition)` with `EnemyData.Visual` or `BattleSceneInitializer._playerVisual`: the view creates the `IUnitVisual` inside `Portrait` (inheriting the enemy mirroring and the hit shake), hides the still image but keeps its sprite as the icon, and hands the visual to `BattleUnitEffectView` as its colour target. Then:

- **Action.** `CurrentActionModel.Set(user, card)` (from `OnCardExecuting`, player and enemy alike) raises `OnActionStarted`; the presenter of that `user` calls `PlayAction`.
- **Hit and defeat** need no wiring of their own: `BattleUnitStatusView.PlayHpChanged` calls `PlayHit` on a negative delta and `SetDefeated` forwards to the visual, so they follow `UnitPresenter`'s existing HP handling.
- **No definition** (an enemy without `_visual`) leaves the still portrait exactly as before.

What the frames look like and how to swap the implementation is "Characters" in @docs/art.md.
